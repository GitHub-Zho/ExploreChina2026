# 网站工程与 SEO/GEO 优化指导手册

> **这份文档写给谁**：接手本项目（或 Jo 的其他网站项目）的 AI 模型与开发者。
> 它回答三个问题：如何设计网站的底层架构、如何安全地改造一个已上线的网站、
> 如何做 SEO 和 GEO 优化。每一条都在本仓库有真实实现，文中直接引用文件路径作为范例。
>
> **使用方式**：新建网站 → 从第一部分开始照做；优化已有网站 → 从第二部分的方法论开始，
> 永远不要跳过"基线快照"一步。

---

## 第一部分：架构设计原则

### 原则 1：单一真源（Single Source of Truth）——最重要的一条

**规则**：任何一个事实（价格、日期、名称、联系方式、文案）只允许存在于一个文件里。
其他所有出现的地方必须通过 import 引用或构建期派生。

**判断方法**（写任何值之前先问）：
1. 这个值会出现在超过一个页面/组件吗？→ 进数据文件
2. 这个值将来会变吗（价格、日期、账号、路线）？→ 进数据文件
3. 改这个值时，需要"搜索全仓库找出所有出现的地方"吗？→ 说明已经违反了本原则

**反面案例（本项目重构前的真实状态）**：南线价格在 `registry.ts` 里是 1688，
在另一个文件的 FAQ 字符串里硬编码成 "$2,598"，在 SEO 描述里是第三个数字 "$2,398"。
三个价格同时挂在线上，用户看到哪个取决于看哪一段。这就是"改一处漏多处"的结构性根源。

**正面实现（本仓库）**：
```
src/data/
├── constants.ts   # 价格数字唯一合法出现地（叶子模块，见原则 2）
├── types.ts       # 全部接口定义（纯类型，永不参与循环依赖）
├── trips/*.ts     # 每个产品一个文件，一个完整类型化对象，包含它的一切
├── registry.ts    # 汇编 + 查询 helper + 派生投影（卡片数据永不手写）
└── site.ts        # 全站配置（email/社交账号/关于页内容），与产品无关
```

### 原则 2：依赖方向单向化，叶子模块承载共享常量

```
constants(叶子) ← trips/*(数据) ← registry(汇编) ← pages/components(消费)
```

- **叶子模块**（`constants.ts`）不 import 任何本地文件 → 永不制造循环依赖，
  且客户端 island 可以安全引用它而不拖入整个数据层。
- **教训（本项目踩过）**：让 React 表单 island 直接 import registry，
  打包体积从 38KB 暴涨到 167KB——全部行程散文被打进了客户端 JS。
  修复方式：island 只 import 叶子常量；产品数据在 `.astro` 页面 frontmatter
  （服务端）算好后作为 **props** 传给 island（见 `src/pages/apply.astro`）。

### 原则 3：派生，不要复制

列表卡片、sitemap、表单选项、结构化数据——凡是"另一种形态的同一份数据"，
一律写成派生函数，绝不手工维护第二份。

- 卡片投影：`registry.ts` 的 `toCardMeta()`——出发日期从 `trip.dates` 派生，
  所以"取消了 6 月批次但卡片还显示 6 月"这类 bug 在结构上不可能发生。
- 结构化数据：`src/data/seo.ts` 的 `tripJsonLd()`——四个行程页共用，
  schema 与页面内容永远一致。
- sitemap / llms.txt：`src/pages/sitemap.xml.ts`、`src/pages/llms.txt.ts`
  在构建期从 registry 生成，加产品自动收录。

### 原则 4：类型即契约，禁止 any

- 数据模型全部定义在 `types.ts`，字段写注释说明约束
  （例：`form.scheduleId 会写入 Google Sheet，对已有产品永不可改`）。
- `any[]` 会掩盖数据文件之间的形状漂移。本项目把 `itinerary: any[]` 换成
  `ItineraryDay[]` 后，类型检查立刻抓到了两处真实的数据缺字段。
- 页面 `<script>` 里为了过类型检查，只允许加**类型标注和非空断言 `!`**
  （编译时擦除，运行时零变化），不允许为了类型改运行逻辑。

### 原则 5：为未来产品族留判别接缝（但不要提前设计）

- 现在的产品类型带 `kind: 'trip'` 判别字段，`types.ts` 里有
  `export type Offering = Trip;` 联合类型。
- 将来加新产品族（如咨询服务）：新建 `Service` 接口（`kind: 'service'`）加入联合，
  渲染处按 `kind` 分流。**不动任何现有代码。**
- **禁止**：往 `Trip` 里塞服务用的可选字段（"顺便复用一下"是类型腐化的开始）；
  在需求明确前凭空设计 `Service` 的字段（必然设计错）。

### 原则 6：双语（多语言）架构

- 内容进数据文件，用扁平 `*Zh` 字段（`title` / `titleZh`）；页面是薄模板。
- 组件接 `lang`/`isZh` prop，不做两份组件。
- 每个 EN 页面必须有 `/zh/` 镜像路由——用门禁强制（见第三部分检查 7），
  否则一定会出现"忘了建中文页"（本项目 `/zh/apply` 曾经就是 404）。
- 允许两种语言内容**有意不同**（本站南线中英文高亮图集就不同），
  但必须在数据文件里注释声明是有意的，防止后人"好心同步"。

### 原则 7：框架选择

营销/转化型网站（广告引流 → 落地页 → 表单）的默认答案是**静态站**
（Astro/Next 静态导出均可）：快、零服务器成本、SEO 友好。
只有一处需要交互状态的地方（如报名表单），用一个 island，不要整站上 SPA。
对"AI 模型维护"的团队，**类型化数据文件 + 构建门禁**优于接 CMS——
改错了构建就红，模型能自我纠错。

## 第二部分：改造已上线网站的方法论

> 网站在赚钱/获客，改坏一次的代价大于慢一点。以下流程在本项目
> 全程执行（8 个阶段、9 个提交），期间零事故并顺手修掉 6 个线上 bug。

### 步骤 0：审计先行，方案后动

并行做三类审计，输出带 `文件:行号` 的实锤清单：
1. **数据一致性**：grep 所有价格/日期/名称字面量，标记每处是引用还是硬编码；
   数据文件之间互相对比同一字段。
2. **重复度**：多语言页面对、组件间的复制粘贴标记/CSS/JS。
3. **工程卫生**：死文件（零 import）、误提交（IDE 配置/构建产物）、
   图片体积、文档与现实的偏差（CLAUDE.md 说的和代码做的是否一致）。

### 步骤 1：建立基线（不可跳过）

```bash
npm run build && cp -R dist /tmp/baseline-dist
```

之后**每个阶段结束**：重新构建，与基线做归一化 diff
（哈希文件名如 `/_astro/x.HASH.js` 先归一化再比，见 `scratchpad/normdiff.sh` 思路）：

> **铁律：diff 里的每一行变化，要么在本阶段的预期清单上，要么就是 bug。**

这条铁律在本项目实际抓到了：转写内容时手滑多加的两个词、
表单 bundle 的 4 倍膨胀、Tailwind 扫描数据文件导致的 CSS 漂移。
没有基线 diff，这三个问题都会带病上线。

### 步骤 2：分阶段，每阶段独立可提交

- 每阶段结束时必须是**绿灯状态**（构建通过、输出可解释），可随时停下。
- 排序原则：先做零输出变化的卫生清理（验证 diff 工具本身），
  再做数据地基，再逐块迁移消费方，工具链固化放在迁移完成后，文档永远最后
  （文档要描述终态）。
- 转写内容时**逐字搬运**，不顺手润色——润色是另一个 PR 的事，
  混在重构里会污染 diff 的可解释性。

### 步骤 3：高危区清单

开工前列出"不许碰"与"必须人工测"：
- 脆弱模块（本站：首页故事动画——CLAUDE.md 明确标注）只动 frontmatter import，
  不动标记/JS/CSS。
- 钱路径（报名表单、支付集成）：结构改动后必须端到端实测
  （本站：预览浏览器里选线路→combo→确认价格计算→测试提交落表）。
- 第三方集成的**魔法字符串**（FormSubmit 与邮箱字符串绑定激活、
  Google Sheet 的 scheduleId 列值）：改法只能是"引用化"，值必须逐字节不变，
  构建后 grep dist 确认。

### 步骤 4：把规则固化成门禁

人（和模型）会忘，构建不会。你修掉的每一类 bug，都应该问一句：
**"什么检查能让这类 bug 永远无法再上线？"** 然后写进门禁（见第三部分）。

## 第三部分：质量门禁设计（scripts/quality-gate.mjs）

本站门禁在 `npm run build` 最前面跑，7 项检查，任何一项失败即构建失败：

| # | 检查 | 防的是什么事故 |
|---|------|----------------|
| 1 | 禁用动态随机图床（source.unsplash.com） | 页面图片每次刷新变化 |
| 2 | 禁用户可见的 figma/notion 链接 | 内部工具链接泄漏给用户 |
| 3 | 页面里的 TBD/TODO 标记 | 占位文案上线 |
| 4 | 引用的 `/images/...` 必须存在于 public/ | 死图（也提供无引用图片清单模式） |
| 5 | 站内 `href="/..."` 必须能解析到真实路由或 redirect | 死链 |
| 6 | **价格字面量禁止出现在 data 目录之外** | "改一处漏多处"的价格事故 |
| 7 | EN↔ZH 路由齐全性 | 忘建另一语言的页面 |

**写完门禁必须红队测试**：每一项检查，故意制造一次违规，确认真的会红，再还原。
"从没红过的检查"和没有检查是一回事。

类型检查（`astro check`）同样进构建管线：`quality && check && astro build`。

## 第四部分：SEO 清单（技术 SEO）

> 按优先级排序。每一项标注了本仓库的实现位置，照抄结构即可。

### 4.1 标题（最高性价比，最常被做错）

- [ ] **转化页的 `<title>` 必须以搜索关键词开头，品牌名放最后**，≤62 字符。
  - 反例（本站曾经的真实状态）：东线页标题就是品牌化的 `Old Souls, New Lights`
    ——搜索引擎从标题里读不到 China/student/trip/Shanghai 任何信号。
  - 正例：`Shanghai to Beijing: 10-Day China Student Trip 2026 | Explore China`。
  - 实现：标题存在数据对象里（`trip.seo.title`/`titleZh`），页面引用，不散落。
- [ ] 每页 title 唯一；双语页各写各的（不要机翻对方）。

### 4.2 Meta 与链接标签（Layout 层统一处理）

- [ ] `<meta name="description">`：每页唯一、150–160 字符、含关键词与行动指向。
  注意 Astro/JSX 中**重复的 description 属性后者静默覆盖前者**——本站曾有
  4 个页面带两个 description 而无人发现。
- [ ] `<link rel="canonical">`：每页显式传入，不依赖运行时 URL。
- [ ] hreflang 三件套：本页语言、对方语言、`x-default`。
  **x-default 指向本页的英文版**，不是首页（本站曾全站指首页，
  更糟的是 apply 页曾输出 `href=".../undefined"`——prop 漏传没有类型兜底）。
- [ ] og:title / og:description / og:image / twitter:card。
  **og:image 必须是自己站的真实图片的绝对 URL**
  （本站曾用一张 Unsplash 外链图做全站分享图）。转化页传该页主图。
  实现见 `src/layouts/Layout.astro`。

### 4.3 结构化数据（JSON-LD）——同时是 GEO 的地基

- [ ] Organization（全站）：name/url/email/**sameAs 数组**（挂社交账号，建立实体关联）。
- [ ] 产品页按业务选 schema 类型（本站 TouristTrip；电商 Product；服务 Service），
  必须带 **offers**（price/priceCurrency/availability）和 image。
- [ ] **页面上有 FAQ 内容就必须有 FAQPage schema**——搜索富摘要 + AI 答案引擎双收益。
  本站曾经首页有 FAQPage、行程页有 FAQ 内容却没有 schema，白白浪费。
- [ ] BreadcrumbList：完整层级（Home → 分类 → 本页），不要跳级。
- [ ] **schema 必须从数据对象派生**（`src/data/seo.ts` 的 `tripJsonLd()`），
  手写的 schema 会和页面内容漂移。
- [ ] 验证：构建后用脚本 `JSON.parse` 每页的 ld+json 确认合法，
  上线后用 Google Rich Results Test 复验。

### 4.4 站点级文件

- [ ] `sitemap.xml`：动态生成，路由从数据注册表派生（加页面自动收录），
  见 `src/pages/sitemap.xml.ts`。
- [ ] `robots.txt`：指向 sitemap；对 AI 爬虫的态度**显式写成注释**
  （见第五部分），防止后人手滑加 Disallow。
- [ ] 部署平台 redirect 规则纳入门禁的内链检查（vercel.json 的 source 算合法目标）。

### 4.5 常见坑（本站全部踩过，已修）

- 同一属性写两遍 → 后者静默生效，另一份成为幽灵文案
- SEO 描述里硬编码价格 → 价格改了描述不改（Google 摘要显示旧价）
- 双语页只有一边有 schema
- 忘给新页面配 hreflang 对（用门禁检查 7 兜底）

## 第五部分：GEO 清单（生成式引擎优化）

> GEO = 让 ChatGPT/Claude/Perplexity 等 AI 助手在回答用户问题时
> **正确地引用你**。对"外国游客问 AI 怎么去中国玩"这类场景，
> GEO 的转化价值可能超过传统 SEO。

- [ ] **`/llms.txt`**：面向 AI 的纯文本站点摘要。内容：一段定位描述、
  每个产品的核心事实（名称/路线/日期/价格/包含什么）、关键页面链接、
  "AI 常被问到的事实"块（签证/退款政策等）。
  **必须动态生成**（本站 `src/pages/llms.txt.ts` 从 registry 派生），
  静态写死的 llms.txt 会在改价后变成向 AI 撒谎的文件。
- [ ] **robots.txt 明确欢迎 AI 爬虫**（GPTBot/ClaudeBot/PerplexityBot/
  Google-Extended…）。默认 `Allow: /` 已覆盖，但要写注释声明这是商业决策，
  防止后人套用"防爬虫模板"误伤。
- [ ] **FAQPage schema 全覆盖**（见 4.3）——AI 答案引擎最直接的喂料格式。
- [ ] **可引用的事实块**：正文里保留短句、自包含、含数字的事实
  （"10 天，CAD $2,488，含住宿与境内交通，不含国际机票"）。
  AI 摘录的是句子，不是布局。
- [ ] **实体一致性**：品牌名、邮箱、社交账号在页面、schema、llms.txt
  三处完全一致（全部引用 `site.ts`，见原则 1）。
- [ ] 内容页的事实性段落不要藏在 JS 交互后面——爬虫看的是静态 HTML
  （静态站天然满足；SPA 需要 SSR/预渲染）。

## 第六部分：执行守则（给接手模型的硬规则）

1. **先读 CLAUDE.md 和本文档**，再读代码；发现文档与代码矛盾，以代码为准，
   并在同一个提交里修文档。
2. **动手前建基线**（`build` + 快照 dist），动手后每阶段 diff。
   解释不了的 diff 行 = bug，不是噪音。
3. **改内容用逐字搬运**；想润色文案，单独开一个提交。
4. 标记为脆弱的区域（本站：首页故事动画）**不碰内部**；
   钱路径（表单/支付）改后必须端到端实测。
5. 新增的每类 bug 修复，写一条门禁检查固化它，并红队测试该检查。
6. 提交信息写清楚"改了什么 + 为什么 + 怎么验证的"；
   分支流程遵守仓库规定（本站：test 预览 → 批准 → main）。
7. 需要业务决策的事（删用户内容、改对外文案口径、账号指向）**问用户，不要假设**；
   纯技术决策（重构结构、加检查）自己定并说明理由。
8. 完成后更新 README/CLAUDE.md 的相关章节——下一个接手的模型只有文档可读。
